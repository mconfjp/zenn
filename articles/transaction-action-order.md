テーマは「トランザクションの中に処理を書く順番」です。
これについて、簡単な指針があるという話をします。

## 課題
トランザクション処理を書いていると、こういう場面に出会います。

- 外部サービスとの連携があって、どこで失敗したらどうなるかを考えないといけない
- トランザクションの中でメールを送るかどうか悩む

例として、ECサイトの注文確定処理を考えます。

```php
// コードの中身は重要じゃないので雰囲気で呼んでください。
// DB::transaction()の中がトランザクションとして実行される
DB::transaction(function () use ($order) {
    // 注文確定メールを送る
    Mail::to($order->user)->send(new OrderConfirmed($order));

    // 注文ステータスを確定にする
    $order->update(['status' => 'confirmed']);

    // 在庫を引き当てる
    foreach ($order->items as $item) {
        $item->product->decrement('stock', $item->quantity);
    }
});
```

在庫の引き当てで失敗すると、トランザクションはロールバックされます。
注文ステータスと在庫はもとに戻りますが、メールはもう送られています。
ユーザーの手元には、確定していない注文の「注文確定メール」が残ります。
あ〜ら困った。

<!-- 図：処理の順番と、在庫引き当て失敗時にロールバックで戻るもの／戻らないもの -->

## 解決方法
:::details 前提
### 前提
トランザクションなので、原子性を担保したいもの^[原子性を担保したいとは: 全部成功するか全部失敗するかのどっちかになって欲しいもの。一部のアクションだけ成功されると困っちゃうもののことを、原子性を担保したいものと呼びます]は全部トランザクションに入れてください。そのうえで、トランザクションの中に入れたものをどう並べるかを以下で説明します。
:::
### 考え方のヒント：処理を「非保護」「保護」「実」に分類する
まずトランザクションの中で行われる処理は３つに分類することが可能です。
Jim Grayの論文 [The Transaction Concept: Virtues and Limitations](https://jimgray.azurewebsites.net/papers/theTransactionConcept.pdf)（1981年）では、トランザクションの中のアクションを、失敗時の扱いによって3つに分類しています。

| 分類               | 失敗時の扱い          | 例                  |
| ---------------- | --------------- | ------------------ |
| 非保護（Unprotected） | 取り消しも再実行も要らない   | 一時ファイルへの書き込み、読み取り  |
| 保護（Protected）    | 取り消しも再実行もできる    | 通常のDB操作            |
| 実（Real）          | いったん実行したら取り消せない | メール送信、現金支払機からの払い出し |

非保護アクションは失敗してもどうでもいいやつです。保護アクションはロールバックすればもとに戻ります。実アクションは、ロールバックしても戻りません。
先ほどの例で困った思いをしたのは、実アクションであるメール送信が実行されたのに、その後に保護アクションが実行され、そこで処理がロールバックされてしまったがために発生しています。

### どうする：実アクションは最後にやる
解決策はシンプルで、実アクションを最後にやります。取り消せないものはなるべく後の方にやることで、その後の失敗の可能性を減らしてあげることができます。
先ほどの実例だと、以下のような感じ。

```php
// 雰囲気で感じてください
DB::transaction(function () use ($order) {
    // 保護：失敗したらロールバックで戻る
    $order->update(['status' => 'confirmed']);
    foreach ($order->items as $item) {
        $item->product->decrement('stock', $item->quantity);
    }

    // 実：取り消せないので最後
    Mail::to($order->user)->send(new OrderConfirmed($order));
});
```

上記の処理順であれば、在庫の引き当てで失敗してもメールは送られません。
### 上記でも困ったら
上記でも困るケースはありえます。例えば実アクションが複数ある場合などです。そんな場合はトランザクショナルアウトボックスパターンを検討してください。細かな解説はしませんが、回避できるケースもあります。
