## これはなに
こんにちは、もりたです。
最近Software Designで連載をしているのですが、その調べものの中で知ったものの、連載原稿には入れられなかったネタをここで消化します。
連載原稿の進捗がほんまにやばいので、めっちゃ簡潔に書きます。

テーマは「トランザクションの中に処理を書く順番」です。
これについて、簡単な指針があるという話をします。

## 課題
トランザクション処理を書いていると、こういう場面に出会います。

- 外部サービスとの連携があって、どこで失敗したらどうなるかを考えないといけない
- トランザクションの中でメールを送るかどうか悩む

例として、ECサイトの注文確定処理を考えます。

```php
DB::transaction(function () use ($order) {
    // 注文確定メールを送る
    Mail::to($order->user)->send(new OrderConfirmed($order));

    // 注文ステータスを確定にする
    $order->update(['status' => 'confirmed']);

    // 在庫を引き当てる
    foreach ($order->items as $item) {
        $item->product->decrement('stock', $item->quantity);
    }
});
```

在庫の引き当てで失敗すると、トランザクションはロールバックされます。
注文ステータスと在庫はもとに戻りますが、メールはもう送られています。
ユーザーの手元には、確定していない注文の「注文確定メール」が残ります。

## 解決方法
### 前提
トランザクションなので、原子性を担保したいものは全部トランザクションに入れてください。
この記事は、そのうえで「中に入れたものをどう並べるか」の話です。

### 処理を「非保護」「保護」「実」に分類する
Jim Grayの論文 [The Transaction Concept: Virtues and Limitations](https://jimgray.azurewebsites.net/papers/theTransactionConcept.pdf)（1981年）では、トランザクションの中のアクションを、失敗時の扱いによって3つに分類しています。

| 分類 | 失敗時の扱い | 例 |
| --- | --- | --- |
| 非保護（Unprotected） | 取り消しも再実行も要らない | 一時ファイルへの書き込み、読み取り |
| 保護（Protected） | 取り消しも再実行もできる | 通常のDB操作 |
| 実（Real） | いったん実行したら取り消せない | メール送信、現金支払機からの払い出し |

保護アクションは、ロールバックすればもとに戻ります。
実アクションは、ロールバックしても戻りません。
先ほどの例で困ったのは、実アクションであるメール送信を、保護アクションより前に置いていたからです。

### 実アクションは最後にやる
指針はシンプルで、実アクションを最後にやります。

- 取り消せるもの（保護アクション）は先にやる。失敗したらロールバックで戻ってもらう
- 取り消せないもの（実アクション）は最後にやる

```php
DB::transaction(function () use ($order) {
    // 保護：失敗したらロールバックで戻る
    $order->update(['status' => 'confirmed']);
    foreach ($order->items as $item) {
        $item->product->decrement('stock', $item->quantity);
    }

    // 実：取り消せないので最後
    Mail::to($order->user)->send(new OrderConfirmed($order));
});
```

こうしておけば、在庫の引き当てで失敗してもメールは送られません。

Grayの論文でも、実アクションはコミットまで遅延させるべきだとしています。
ログに実行予定として積んでおき、コミットが成功してから実行する、という方式です。

### 取り消せないものが複数あったら
メール送信と外部の決済APIの呼び出しのように、実アクションが複数ある場合は、並べ替えだけでは解決しません。
1つ目が成功して2つ目が失敗すると、1つ目は取り消せないからです。

この場合は、トランザクショナルアウトボックスパターンなどを検討してください。
実アクションを「実行予定」としてDBに書き込み（これは保護アクションになる）、コミット後に別プロセスが実行する方式です。
先ほどのGrayの「ログに積んでおいてコミット後に実行する」とほぼ同じ形をしています。

## おわりに
簡単な解説でした。
自分はこれでどうにかなっていますが、うまくいかないケースもあるかもしれません。
そういうケースを知っていたら、コメント欄などに書いておいてください。
そうしたらみんな賢くなってハッピーです。
