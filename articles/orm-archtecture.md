## リード文
連載の第4回はORMのアーキテクチャです。システムのアーキテクチャ選定は将来のシステム拡張性に影響を与える重要な意思決定です。ORMはデータアクセス層とドメイン層に接しており、両面のアーキテクチャに影響を与えます。今回はORMの代表的なアーキテクチャを整理し、それがシステム全体のアーキテクチャにどう影響するのかを見ていきます。

## 第4回：ORMのアーキテクチャ
ソフトウェアのアーキテクチャ選定は難題です。初期の意思決定がその後の設計に広く影響し、かつやり直しには大きなコストがかかります。その中でも特に厄介なのがORMの選定です。本来ORMはアプリケーション全体にとってデータアクセスのための道具にすぎませんが、時にORM自身の都合でアプリケーションを振り回してしまうこともあります。

そのように影響の大きな意思決定になるにもかかわらず、ORMのアーキテクチャについての議論は大雑把なものが目立ちます。ORMのアーキテクチャ選定についてWebで検索すると、次のような説明に出会うでしょう。

> ORMにはActiveRecordパターンとDataMapperパターンが存在する
 
 > ActiveRecordパターンは業務ロジックがシンプルな場合に向いており、DataMapperパターンは業務ロジックが複雑な場合に向いている

これらの説明は間違ってはいません。ただ、2つの点で補足が必要だと筆者は考えています。1つは、ORMのアーキテクチャは2種類だけではないという点です。もう1点は「業務ロジックがシンプル／複雑」という判断基準が曖昧である点です。その内実を知ることなしに基準たりえず、自信を持ってアーキテクチャを選定することは難しいでしょう。

今回は上記の点を修正・補足し、ORMのアーキテクチャに関するより正確でシンプルな議論を提供します。全体の構成としてはORMのアーキテクチャ選定における前提となる考え方を説明したのち、各アーキテクチャの詳細をそれぞれ解説します。

## 前提
それでは、ORMのアーキテクチャについての具体的な議論に入る前に、その前提を整理しましょう。
ORMというミドルウェアのアーキテクチャについて我々が語るとき、我々は何を整理しようとしているのでしょうか？　その答えは責務と構造です。つまり、「何を目的としたソフトウェアなのか？」「どのように組み立てて構成するか？」を考えることになります。
ここではまず、より抽象度の高い責務の整理を行います。それを以て、後半に続く具体的な議論に入るにあたっての橋頭堡としたいと思います。また、責務の整理をする上で、ORMの責務と密接に関わる「ドメインロジック」についても簡単に整理します。
### ORMの責務の整理
まずはORMの責務です。筆者は大きく３つあると考えています。

**SQLの発行**：アプリケーションからの要求をSQLに変換し、RDBに対して実行する
**構造的マッピング**：SQLの結果セットを、ドメインロジックが利用するオブジェクトの形に変換する
**振る舞いのマッピング**：ユニットオブワークやアイデンティティマッピングなど、オブジェクトの読み込みと保存に関する制御を行う

![](https://static.zenn.studio/user-upload/79d4a6a5fccf-20260926.png)

この3つの責務には濃淡があります。
SQLの発行は、どのORMでも責務として挙げられます。構造のマッピングはORMごとに責務として持つ・持たないに差が出やすいです。振る舞いのマッピングは、前回見たとおり責務としては縮小傾向であり、採用されるケースが限られます。
つまりORMごとの個性が出やすいのは構造的マッピングになります。構造のマッピングを色濃く採用したORMと、それを薄く対応したORMの間には機能性のみならず構造にも差異が現れます。そしてそれを我々はアーキテクチャと呼びます。
### ドメインロジックについて
ではなぜ構造的なマッピングには責務の度合いに差が出るのでしょうか？
その理由は、構造的なマッピングのニーズが利用者によって様々だからです。前提として、構造的なマッピングとはSQLの結果セットとドメインロジックで利用されるオブジェクトとの間で生じる構造的な変換です。利用者であるドメインロジックの求めるオブジェクト次第では、構造的なマッピングに求められるものも変わってきます。すなわち、ORMのアーキテクチャはドメインロジックのパターンに依存します。

以下に『エンタープライズアプリケーションアーキテクチャパターン』（以降、『PoEAA』）から引用して、次の４つドメインロジックを紹介します^[『PoEAA』第9章「ドメインロジックパターン」。同章にはサービスレイヤも含まれますが、これはほかのパターンの上に載せる層なので、ここでは除外しています。]。

- **トランザクションスクリプト**：1つの要求を、1つの手続きで処理する形。手続きの中でRDBを直接、または薄いラッパー越しに呼び出す
- **テーブルモジュール**：テーブル1つにつき1つのクラスを用意し、そのクラスの1インスタンスがテーブルの全行に対するビジネスロジックを持つ形。データはクラスの外にある結果セットを参照する
- **シンプルなドメインモデル**：データと振る舞いを一体にしたオブジェクトでドメインを表現する形のうち、オブジェクトの構造がテーブルの構造にほぼ一致するもの
- **リッチなドメインモデル**：ドメインモデルのうち、継承や細かなオブジェクトの絡み合いを含み、テーブルの構造とは一致しないもの

冒頭では『業務ロジックがシンプルならActiveRecord、複雑ならDataMapper』という一文を引用しました。しかしこのように、ドメインロジックはシンプル／複雑の二元論ではありません。ドメインモデル以外のドメインロジックを採用したケースを考慮したとき、ORMのアーキテクチャも自然とActiveRecord／DataMapperの二元論では語れなくなると気がつくでしょう。

表1 - ORMのアーキテクチャの分類

| アーキテクチャ       | 返却されるオブジェクトの形        | 状態を持つか  | ドメインロジックを持つか |
| ------------- | -------------------- | ------- | ------------ |
| テーブルデータゲートウェイ | 変換しない（結果セットのまま）      | 論点にならない | 持たない         |
| 行データゲートウェイ    | 変換しない（テーブル準拠のオブジェクト） | 持つ      | 持たない         |
| アクティブレコード     | テーブル準拠のオブジェクト        | 持つ      | 持つ           |
| データマッパー       | ドメインモデル準拠のオブジェクト     | 持たない    | 持たない         |

最も重要な分類の軸は「返却されるオブジェクトの形」です。前節で見たとおり、ORMの個性が出やすいのは構造的マッピングなので、マッピングの結果がどんな形になるかでアーキテクチャを分類するのが自然です。この軸で見ると、4つのパターンは大きく2つのグループに分かれます。テーブルデータゲートウェイと行データゲートウェイには変換先のドメインモデルが存在しません。結果セットをそのまま返すか、テーブルの行に準拠したオブジェクトを返します。対してアクティブレコードとデータマッパーには変換先のドメインモデルが存在し、前者はシンプルなドメインモデル、後者はリッチなドメインモデルに対応したオブジェクトを返します。

また、上記に加えて、「状態を持つか」「ドメインロジックを持つか」という点も分類軸として追加しています。「状態を持つか」は、クエリを発行するオブジェクトが結果のオブジェクトを自身のプロパティとして保持するか、それとも呼び出し元に渡して手放すかという違いです。「ドメインロジックを持つか」は、ORMのオブジェクト自身がビジネスのルールを持つかどうかという違いです。この2つはアプリケーションのアーキテクチャへの影響度合いが大きいため、ここで紹介しています。

ここからは、4つのアーキテクチャを1つずつ見ていきます。それぞれについて、概要、相性のよいドメインロジック、現代の実例の順に説明します。また、コード例として体重管理アプリでのコードを例示します。コードの流れは全て「身体情報を取得する→リクエスト内の体重情報を使ってBMIを計算する→体重とBMIを保存する」としているので、アーキテクチャごとの違いを見比べてみてください。

### テーブルデータゲートウェイ
#### 概要
テーブルデータゲートウェイ（Table Data Gateway）は、対象のテーブルに対するSQLをひとつのクラスにまとめたものです。1つのインスタンスがそのテーブルの全行を扱い、find系のメソッドと、insert、update、deleteの各メソッドを持ちます。オブジェクト自身は状態を持たず、データの受け渡しだけを行います。

『PoEAA』ではテーブル1つにつき1つのゲートウェイを用意するのが基本とされていますが、厳密な定義ではありません。実態としては、SQLに名前を付けて呼び出せるようにしたクエリのラッパーと考えるとよいでしょう。

クエリを発行した結果は、構造的なマッピングは行われず結果セットのまま配列などの汎用的な入れ物に入れて返されます。ただ、結果が汎用的な入れ物で返ってくると、データベース側のカラム名変更などが起きた場合に返却される結果セットの中身が変わってしまい、容易に実行時のエラーにつながります。
現代ではスキーマやSQLから結果の型を自動生成するライブラリが登場したことでこの弱点は解消されつつあります。

```typescript
// TypeScript/Prismaによる実例
async function recordWeight(id: number, weight: number) {
  // 身体情報を取得する
  const profile = await prisma.bodyProfile.findUniqueOrThrow({ where: { id } });

  // リクエスト内の体重情報を使ってBMIを計算する
  const bmi = weight / (profile.height / 100) ** 2;

  // 体重とBMIを保存する
  await prisma.bodyProfile.update({
    where: { id },
    data: { weight, bmi },
  });
}
```
#### 相性の良いドメインロジック
相性がよいドメインロジックはトランザクションスクリプトです。変換先のドメインモデルを必要とせず、必要なデータをスクリプト上で取ってきてはそのまま使う、というシンプルな作りになるためです。
『PoEAA』では、共にテーブル単位でオブジェクトを扱うという観点からテーブルモジュールとの相性の良さが解説されています。ただ、現代においては複数テーブルをJOINしてクエリを発行することがほとんどでです。純粋に１テーブルだけを利用するテーブルデータゲートウェイの利用機会がなくなり、同時にテーブルモジュールを採用するメリットも無くなってしまったため、今回は相性の良いドメインロジックからは外しています。
#### 実例
現代の実装例としては、GoのsqlcとTypeScriptのPrismaが挙げられます。
sqlcは、開発者が書いたSQLからGoの関数と結果の構造体を生成するツールです。生成された関数はSQLの薄いラッパーで、結果は型付きの構造体で返ります。テーブル構造が変われば生成される型も変わるので、綴りミスや構造変更はコンパイル時に検出されます。かつてのテーブルデータゲートウェイの弱点をくコード生成で解消した形と言えます。
Prismaも同様で、スキーマ定義からDBアクセス用クライアントを生成されます。このクライアントにはテーブルごとの検索・更新関数が生えています。

### 行データゲートウェイ
#### 概要
行データゲートウェイ（Row Data Gateway）は、読み込みと書き込みで２系統のクエリ発行処理を持ちます。読み込みではFinderと呼ばれるゲートウェイのクライアントがクエリを発行し、結果を取得します。書き込みでは、DBレコードの1行に相当するインスタンスが、自身に対する書き込みのメソッドを持っています^[実装によっては異なるケースも存在します]。
また、結果オブジェクトを自身のプロパティとして保持することも特徴です。プロパティはDBテーブルのスキーマ構造と同じ構造となり、オブジェクト自身がレコードに、プロパティが各カラムに相当します。

```go
// Go/entによる実例
func RecordWeight(ctx context.Context, client *ent.Client, id int, weight float64) error {
	// 身体情報を取得する
	p, err := client.BodyProfile.Get(ctx, id)
	if err != nil {
		return err
	}

	// リクエスト内の体重情報を使ってBMIを計算する
	bmi := weight / math.Pow(p.Height/100, 2)

	// 体重とBMIを保存する
	_, err = p.Update().
		SetWeight(weight).
		SetBmi(bmi).
		Save(ctx)
	return err
}
```

#### 相性の良いドメインロジック
相性がよいドメインロジックはトランザクションスクリプトです。
また、トランザクションスクリプトを書いていく中で、特定のテーブルで同じドメインロジックを重複して書くことに気がつくことがあります。その際は行データゲートウェイに共通のビジネスロジックを持たせることで、シンプルなドメインモデルとして扱うこともできます。この場合、行データゲートウェイはアクティブレコードに移行します。
#### 実例
現代の実例としては、Goのentが挙げられます。entはGoのコードでスキーマを定義し、そこからクライアントとエンティティのコードを生成するORMです。クライアント経由でクエリを発行すると、結果はテーブル準拠の構造体で返ってきます。この構造体自身が更新用のビルダーとなるメソッドを持っており、取得した行から続けて更新クエリを発行できます。行ごとに状態を持ち、行のオブジェクト自身がSQLを発行できる、という行データゲートウェイの形をそのまま体現しています。

### アクティブレコード
#### 概要
アクティブレコード（Active Record）は行データゲートウェイにドメインロジックを足したものです。行データゲートウェイと同じように、クエリの結果オブジェクト自身が状態をもちデータベースアクセスのロジックを持つほか、ドメインロジックをも持っています。クラスの構造はテーブルの構造と一致する点も行データゲートウェイと同じです。
若干注意が必要なのは、ドメイン層とデータアクセス層をレイヤーとして分割しない点です。そのため、ドメイン層がデータアクセス層に依存し、ドメイン層のみでテストができないという問題があります。また、データベーステーブルが複数のビジネスコンテキストで利用される場合に、一つのドメインモデルに複数のビジネスコンテキストが混ざりやすいという課題も持っています^[これらのデメリットがありながらもRailsのActiveRecordは広く採用されています。その思想や意図、問題点は次のテックブログでまとめましたので、気になる方は確認してみてください：{{ここにリンクを入れる}}]。

```ruby
# Ruby/Active Recordによる実例
class BodyProfile < ApplicationRecord
  def record_weight(new_weight)
    self.weight = new_weight
    self.bmi = new_weight / (height / 100.0)**2
  end
end

# 身体情報を取得する
profile = BodyProfile.find(id)

# リクエスト内の体重情報を使ってBMIを計算する
profile.record_weight(weight)

# 体重とBMIを保存する
profile.save!
```

#### 相性の良いドメインロジック
相性がよいドメインロジックは、当然シンプルなドメインモデルです。アクティブレコードパターンの定義上、シンプルなドメインモデル以外の選択肢は存在しません。
#### 実例
最も有名な実装はRuby on RailsのActive Recordです。
Railsの思想はCoC（Convention over Configuration、設定より規約）と呼ばれ、設定を長々と書く代わりに命名ルールなどのRailsの流儀に乗ることで記述量を減らします。RailsのActive Recordも当然CoCの思想の上にあり、フレームワークの提供する基底クラスを継承してドメインクラスを作ります。継承するだけで、クラス名からテーブルが、属性名からカラムが、規約に従って自動的に対応づけられます。データアクセスのためのコードを書かずに済むのが最大のメリットです。アクティブレコードパターン自体は行データゲートウェイにドメインロジックを持たせたものという定義ですが、RailsのActive Recordのような方式がアクティブレコードパターンのデファクトスタンダードだと考えて良いでしょう。

### データマッパー
#### 概要
データマッパー（Data Mapper）は、ドメインロジックとRDBとの間に置かれ、両者の独立性を保ちながらデータを変換するレイヤーです。データマッパー自身は状態やドメインロジックも持たず、リッチなドメインモデル準拠のオブジェクトを返却します。
データベーステーブルとドメインモデルの間にある構造的なギャップを吸収できるORMは4つの中でデータマッパーだけです。そのため狭義のORMといえばDataMapperを指し、最も伝統的・正統派なORMの形であるともいえます。
#### 相性の良いドメインロジック
相性がよいドメインロジックはリッチなドメインモデルです。構造的なマッピングをORMに任せることでドメインロジックにデータアクセス層の知識を持ち込まずに済みます。それによりドメインモデルのテスト容易性を毀損することもありません。リッチなドメインモデルの強みを活かしやすいORMと言えます。
#### 実例
現代の実例ではJavaのHibernateといった伝統的なORMやPHPのDoctrineが挙げられます。前回見たユニットオブワークやアイデンティティマッピングを備えているのも、この系統のORMになります。


```PHP
// PHP/Doctrineによる実例
#[ORM\Embeddable]
final class BodyMeasurement
{
    #[ORM\Column] private float $weight;
    #[ORM\Column] private float $height;
    #[ORM\Column] private float $bmi;

    public function __construct(float $weight, float $height)
    {
        $this->weight = $weight;
        $this->height = $height;
        $this->bmi = $weight / ($height / 100) ** 2;
    }

    public function withWeight(float $weight): self
    {
        return new self($weight, $this->height);
    }
}

#[ORM\Entity]
#[ORM\Table(name: 'body_profiles')]
class BodyProfile
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private int $id;

    #[ORM\Embedded(class: BodyMeasurement::class, columnPrefix: false)]
    private BodyMeasurement $measurement;

    public function recordWeight(float $weight): void
    {
        $this->measurement = $this->measurement->withWeight($weight);
    }
}

// 身体情報を取得する
$profile = $entityManager->find(BodyProfile::class, $id);

// リクエスト内の体重情報を使ってBMIを計算する
$profile->recordWeight($weight);

// 体重とBMIを保存する
$entityManager->flush();
```

## おわりに
以上でORMのアーキテクチャについての解説はおしまいです。
しばしばActiveRecordとDataMapperの２パターンだけだと思われがちなORMですが、実際はテーブルデータゲートウェイや行データゲートウェイといったパターンも存在します。これらはドメインロジックが求める構造的なマッピングの形によって選定されてきました。

また現代的な視点でこの選定基準を見てみると、生成AIによる開発が前提となった時代においては、構造的なマッピングを自前で実装することも可能です。となればテーブルデータゲートウェイのような薄いORMをベースに導入し、コアなビジネスドメインについては構造的なマッピングの層を入れるというような意思決定も可能になるはずです。実際、sqlcはgo言語では人気のあるORMであり、薄いORMを導入し必要に応じて処理を追加するという手法も開発の現場では出始めているようです^[goのsqlcへ移行した事例：https://speakerdeck.com/sgash708/aitogong-nisheng-kiruji-shu-xuan-ding-2026]。生成AI時代にORMをめぐる考え方がどう変わっていくのかを考える本連載においても、アーキテクチャは重要な観点の一つです。

次回は現代においてもう一つ問題になりやすいリポジトリ層について扱う予定です。リポジトリはドメインモデルとORMの間に挟まるもう1つの層です。ORMがあるのになぜリポジトリが必要なのか、そもそも何を抽象化しているのかについて整理します。お楽しみに〜〜！！
