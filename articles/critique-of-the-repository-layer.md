## リード
第五回では、ドメイン層とORMの間に置かれるリポジトリ層を取り上げます。リポジトリ層はデータ永続化を抽象化する層として長い歴史があり、議論の中には混乱しやすい箇所があります。本稿ではその箇所を整理します。
また、今回でこの連載は最終回です。最後にこれまでの振り返りと、連載では扱えなかった論点を示します。

## はじめに
リポジトリ層はドメイン層とORMの間に置かれる層であり、本来はORMのスコープの外にあります。ただし、DDDの文脈でORMを利用する場合、ORMに関連してリポジトリ層をどう取り入れるかが論点になります。本稿では、リポジトリ層をめぐる代表的な批判を取り上げてその背景を整理し、リポジトリ層を導入するかどうかの判断材料を提供します。

## リポジトリ層の定義
### 基本的な定義
詳細な議論や批判の項目に入る前に、リポジトリ層の定義を整理します。

リポジトリ層とはドメインオブジェクトをメモリ上のコレクションとして提供し、その具体的な取得方法やデータソースをドメイン層から隠蔽する層です^[リポジトリ層の定義は『エンタープライズアプリケーションアーキテクチャパターン』（以降、『PoEAA』）と『エリック・エヴァンスのドメイン駆動設計』（以降、『DDD』）に拠ります。どちらもリポジトリ層について言及した最初期の資料であり、特に後者はDDDの文脈から整理した資料として重要です]。

リポジトリ層を置くことで、アプリケーションは次のメリットを得ます。

- ドメイン層の独立：ドメイン層はデータアクセスの仕組みに直接依存せず、リポジトリのインタフェースにだけ依存する。これによりテストが容易になり、データソースの入れ替えもしやすくなる
- アクセスできるエンティティの明示：『DDD』はリポジトリを集約ルートに対して用意するとしており、リポジトリの有無によりどのエンティティに外から直接アクセスしてよいかが示される

以下にコード例を示します。ブログのアプリケーションを題材に、記事（Post）のタイトルを変更する機能を、ドメインモデル、リポジトリ（インタフェースとDoctrineによる実装）、アプリケーションサービスで組み立てます。アプリケーションサービスがリポジトリから記事を取り出し、ドメインモデルの振る舞いを呼び、リポジトリに保存を任せることで機能を実現します。

```php
// ドメイン層：記事
#[ORM\Entity]
class Post
{
    // ...マッピングの定義は省略

    public function rename(string $title): void
    {
        if ($this->isPublished()) {
            throw new DomainException('公開済みの記事はタイトルを変更できません');
        }
        $this->title = $title;
    }
}

// ドメイン層：リポジトリのインタフェース
interface PostRepository
{
    public function byId(int $id): ?Post;
    public function save(Post $post): void;
}

// インフラストラクチャ層：Doctrineによる実装
final class DoctrinePostRepository implements PostRepository
{
    public function __construct(private EntityManagerInterface $em) {}

    public function byId(int $id): ?Post
    {
        return $this->em->find(Post::class, $id);
    }

    public function save(Post $post): void
    {
        $this->em->wrapInTransaction(function () use ($post): void {
            $this->em->persist($post);
        }); // flush時に変更が検知され、UPDATEが発行される
    }
}

// アプリケーション層：記事のタイトルを変更する
final class RenamePostAppService
{
    public function __construct(private PostRepository $posts) {}

    public function __invoke(int $postId, string $title): void
    {
        $post = $this->posts->byId($postId); // リポジトリから取り出す
        $post->rename($title);               // ドメインの振る舞いを呼ぶ
        $this->posts->save($post);           // リポジトリに保存を任せる
    }
}
```

### 補足：リポジトリ層の2つの前提
ここで、リポジトリ層の定義について注意が必要な点を2つ挙げます。
一つ目は、リポジトリ層が返すものを「ドメインオブジェクト」のコレクションだと明示している点です。つまり、リッチなドメインモデルやデータマッパー系のORMと組み合わせることが想定されています。
二つ目は、リポジトリ層を集約ルートに対して作るとしている点です。すべてのエンティティと1対1でリポジトリを作るのではなく、DDDの集約を採用したうえで、その集約ルートに対してだけ作ります。

これらの想定は、リポジトリ層に関する議論では前提として扱われ、表立って触れられないことがあります。そのため、ドメイン層の独立や保守性の向上にだけ着目してリポジトリ層を入れようとすると、この前提が意識されないまま導入が進むことがあります。

もう一つ、データアクセスの抽象化は歴史が長く、さまざまな名前で議論されてきました。リポジトリ層も例外ではなく、『PoEAA』や『DDD』での定義はあるものの、データアクセスを抽象化する層としてひとまとめにされ、定義が曖昧なまま議論されることが少なくありません。

前提が暗黙になりやすいことと、定義が曖昧なまま使われること。この2つが、リポジトリ層をめぐる議論をややこしくしています。本稿ではこの点に留意しながら、次の3つの批判を整理します。

- リポジトリ層はパフォーマンス改善が難しい
- リポジトリ層はアクティブレコードと組み合わせにくい
- リポジトリ層はトランザクションを引き回すことになる

## よくある批判
### パフォーマンス改善が難しい
#### 批判の背景
一つ目の批判は、リポジトリ層を導入するとデータベースのパフォーマンス改善が難しくなるというものです。2010年前後のブログ記事などで散見される批判で、理解するにはいくつかの背景知識が必要です。

当時のリポジトリ層では、ジェネリックリポジトリという書き方が広まっていました。これはエンティティの型を型引数に受けて生成するリポジトリで、CRUDと汎用的な検索メソッドを備えています。検索条件は仕様オブジェクトと呼ばれるオブジェクトとして外から渡し、任意のデータを取得します。当時の.NET界隈でよく見られた形を、C#で示します。

```csharp
// ジェネリックリポジトリ：どのエンティティにも同じインタフェースを提供する
public interface IRepository<T>
{
    IList<T> FindAll(ISpecification<T> spec);
}

// 仕様オブジェクト：検索条件を表す
public class PublishedPostsBy : ISpecification<Post>
{
    public PublishedPostsBy(User author) { /* ... */ }
    // ...条件を組み立てる処理は省略
}

// 記事一覧でも、ダッシュボードでも、同じ仕様を使い回す
var posts = repository.FindAll(new PublishedPostsBy(author));
```

仕様オブジェクトは、同じ条件で検索したい複数の呼び出し元で共有されることがよくありました。ここでパフォーマンスに問題が出て、関連テーブルの読み込み方^[第2回で解説したロード戦略のことです]を指定したくなると、仕様オブジェクトにロード戦略も持たせる必要が生まれます。しかし呼び出し元ごとに必要なロード戦略は異なるので、一つの仕様に複数の要件を書き込むことになり、対応しきれずにパフォーマンスの課題を抱えることがありました^[参考: https://ayende.com/blog/4784/architecting-in-the-pit-of-doom-the-evils-of-the-repository-abstraction-layer]。

#### 批判の整理
この批判の矛先が向いているのは、仕様オブジェクトを複数の呼び出し元で共有する書き方であって、リポジトリ層そのものではありません。ロード戦略は呼び出し元ごとに異なるのですから、仕様オブジェクトも呼び出し元ごとに分け、それぞれがロード戦略を持てばよいだけです。複数の変更理由を持つコードは単一責任の原則からいっても推奨されず、共有すべきでないものを共有させたという書き方の問題にすぎません。

なお、ジェネリックリポジトリや仕様パターンの考え方はORMやその周辺ライブラリに取り込まれており、自前で用意することは少なくなっています。現在の仕様パターンの実装には、仕様にロード戦略を持たせられるものもあるようです^[Spring Data JPAの`Specification`や.NETのArdalis.Specificationなど]。

### アクティブレコードと組み合わせにくい
#### 批判の背景
二つ目の批判は、アクティブレコードパターンのORMを使っているとリポジトリ層を導入しにくい、というものです。

この批判の背景には、アプリケーションの典型的な成長の仕方があります。アクティブレコードパターンはWebフレームワークと一体となって開発速度を出しやすく、事業の立ち上げ期に選ばれることが多いORMです。そのアプリケーションが事業の成長とともに複雑なドメインロジックを抱えるようになると、DDDの戦術的設計を取り入れたくなります。このときに、立ち上げ期を支えたアクティブレコードとの相性が問題になる、というのがこの批判の構造です。

アクティブレコードパターンにはいくつかの特徴がありますが、ここで問題になるのは一点です。ドメインモデル自身がSQLを発行する機能を持っており、ドメイン層とデータアクセスが分離されていないことです。リポジトリ層はこの2つを分離する層なので、アクティブレコードを使ったアプリケーションに持ち込むには、次の2つの作業が必要になります。

- ORMと一体になったドメインモデルを、ORMから切り離して作り直す
- 読み込み時/書き込み時にそれぞれ自前のドメインモデルとORMのモデルとのマッピングコードを用意する

一つ目は既存のドメインモデルに大きく手を入れることになり、負担が大きくなります。二つ目は構造的なマッピングという大きな責務を自前で保守管理することになり、こちらも軽い作業ではありません。
以下に、修正前後のコードを示します。

```php
// 修正前（アクティブレコード）：ドメインモデルがクエリ発行の機能を持つ
class Post extends Model
{
    public function rename(string $title): void
    {
        if ($this->published_at !== null) {
            throw new DomainException('公開済みの記事はタイトルを変更できません');
        }
        $this->title = $title;
        $this->save(); // 自分でUPDATEを発行する
    }
}

// 修正後・作業1：ドメインモデルをORMから切り離す
final class Post
{
    // ...コンストラクタとゲッターは省略

    public function rename(string $title): void
    {
        if ($this->publishedAt !== null) {
            throw new DomainException('公開済みの記事はタイトルを変更できません');
        }
        $this->title = $title; // メモリ上のオブジェクトを変えるだけ
    }
}

// 修正後・作業2：リポジトリの実装で、Eloquentのモデルに詰め替えて保存する
final class EloquentPostRepository implements PostRepository
{
    public function save(Post $post): void
    {
        $row = PostModel::findOrNew($post->id());
        $row->title = $post->title(); // マッピングのコード
        $row->published_at = $post->publishedAt(); // マッピングのコード
        $row->save();
    }
}
```

修正前は、`Post` 一つがドメインルールの判定と更新の発行を兼ねていました。修正後は、切り離した `Post` がドメインルールの判定を受け持ち、更新の発行はリポジトリの実装が受け持ちます。そして両者の間の詰め替えも、リポジトリの実装に自分で書くことになります。一つのクラスで済んでいたものが、ドメインモデル、リポジトリのインタフェース、その実装の三つに分かれ、詰め替えのコードはその後も保守し続ける必要があります。

#### 批判の整理
この批判は的を射ています。アクティブレコードは、ドメインモデルとデータアクセスを分離しないことで開発速度を得る設計です。一方、リポジトリ層は両者を分離するための層であり、補足で述べたとおり、分離されたドメインモデルを前提にしています。分離しない設計の上に分離を前提とした層を載せようとしているのですから、その溝を埋める作業が重くなるのは当然です。

そのため、実際にはアクティブレコードとリポジトリ層を組み合わせること自体を避ける判断が多いようです。Railsの作者であるDHHは、アクティブレコードは永続化の実装を差し替えられるものではないと明言しています^[David Heinemeier Hansson「Active Record vs Data Mapper in Rails」https://dhh.dk/arc/000209.html]。Laravelでも、リポジトリ層を無理に導入せずEloquentを直接使うことを勧める記事が存在します^[例としては次の記事など: https://zenn.dev/yumemi_inc/articles/ce7d09eb6d8117 ]。

### トランザクションを引き回すことになる
#### 批判の背景
三つ目の批判は、リポジトリ層の裏にデータベースを隠すと、トランザクションをうまく扱えなくなるというものです。複数のエンティティにまたがる更新を1つのトランザクションで行おうとすると、リポジトリ層がそれを妨げるように見えます。

この問題は、リポジトリをエンティティごと、つまり実質的にはテーブルごとに用意したときに起きます。エンティティごとにリポジトリがあると、複数のエンティティにまたがる更新では複数のリポジトリを呼ぶことになります。各リポジトリが自分でトランザクションを張ると、更新は別々のトランザクションに分かれてしまいます。1つにまとめるには、アプリケーション層でトランザクションを開始し、各リポジトリに渡して回るしかありません。

```php
// エンティティごとのリポジトリ
interface PostRepository
{
    public function byId(int $id): ?Post;
    public function save(Post $post, Transaction $tx): void;
}

interface CommentRepository
{
    /** @return list<Comment> */
    public function ofPost(Post $post): array;
    public function saveAll(array $comments, Transaction $tx): void;
}

// アプリケーション層：記事を非公開にし、コメントも非公開にする
final class UnpublishPostAppService
{
    // ...コンストラクタは省略

    public function __invoke(int $postId): void
    {
        $tx = $this->db->beginTransaction();      // アプリケーション層でトランザクションを開始し
        $post = $this->posts->byId($postId);
        $post->unpublish();
        $comments = $this->comments->ofPost($post);
        foreach ($comments as $comment) {
            $comment->hide();
        }
        $this->posts->save($post, $tx);           // 各リポジトリに渡して回る
        $this->comments->saveAll($comments, $tx);
        $tx->commit();
    }
}
```

これでは、リポジトリ層で隠したはずのデータアクセスの都合がアプリケーション層に現れ、層の分離が崩れてしまいます^[DoctrineではEntityManagerがトランザクションを握っているため、実際にはこのように渡して回る必要はありません。この批判が切実なのは、トランザクションを明示的なオブジェクトとして扱う環境です。本稿ではわかりやすさを優先し、その環境での書き方をPHP風に示しています。]。

#### 批判の整理
この批判が成り立つのは、リポジトリをエンティティごとに作った場合です。『DDD』の定義では、リポジトリは集約ルートに対してだけ用意します。集約は、常に整合していなければならないビジネスルールを守るための境界です。どの不変条件をひとまとめに守るかはドメインの知識ですが、それは同時に、どの範囲を1つのトランザクションで更新するかというシステムの知識でもあります。集約はこの2つを一致させる単位であり、1つのトランザクションで変更する集約は1つになります^[Vaughn Vernon「Effective Aggregate Design」（2011年）。複数の集約を1つのトランザクションで変更してよい例外についても、同じ論考で扱われています。]。

集約ごとにリポジトリを用意し、1つのトランザクションで変更する集約を1つに限れば、そのトランザクションで呼ぶリポジトリも1つになり、渡して回る相手がなくなります。1つのトランザクションで複数の集約を変更したくなるなら、それは集約の境界を引き直すきっかけです^[集約の境界をどう引くか、集約をリポジトリでどう実装するかといった問題は、紙幅の都合で本稿では割愛します。]。

## 今回のまとめ
今回はリポジトリ層に向けられる代表的な批判を3つ取り上げました。いずれも、リポジトリ層が暗黙に置いている前提（分離されたドメインモデルを想定し、集約ごとに用意する）と食い違う使い方をしたときに表面化する問題だと整理できます。

もちろん、前提と食い違うことを承知のうえで、デメリットを許容しながらレイヤー分離のメリットを取りにいく選択もあります。その判断の材料として、本稿を使ってもらえればと思います。

## 連載のおわりに
以上で本連載は終わりです。
この連載は「ORMは必要か？」という疑問に端を発しています。
単なるSQLの生成機でしかないと思われがちなORMですが、その役割はSQLの生成にはとどまりません。クエリ発行、構造的なマッピング、振る舞いのマッピングという３つの大きな責務と、ロード戦略のようなデータアクセス層に特徴的な課題意識の抽象化を役割に持ちます。
また、DDDの文脈ではドメイン層をデータアクセス層から分離する責務も持っています。これはアプリケーションのドメインロジックによっては大きな問題となります。ORMがSQLの生成を主眼に持つか、それ以上の問題を解決するかはドメインロジックの形に影響を受けます。
アプリケーションと永続化層の間にあるギャップは今後もなくならないはず。この連載で確認した点を前提に、より良い技術選定に活かしてもらえれば幸いです。

とはいえ、この連載でORMについて扱えたのはまだまだ表面的な部分です。次に何を学ぶかの道標として、扱えなかった観点を挙げておきます。

- 製品やアーキテクチャの詳細：連載ではORMの責務を整理し、アーキテクチャにも軽く触れました。個々の製品がその責務をどう実装しているか、またアーキテクチャにはまだ解説できる点が多く、どちらも掘り下げる余地があります
- 型とテスト：どちらもORMの議論で主眼になることは少ないものの、現代のシステム開発では欠かせない要素です。ORMがこれらにどう対応しているかは、ORMを別の角度から理解する手がかりになります
- アクティブレコードとの付き合い方：今回触れたとおり、事業の成長とともに現実の課題になります。アーキテクチャを移行する/しないに関わらず、複雑化したアクティブレコードをどう解いていくかは主題になり得ます
- 生成AI時代のORM：コードの多くを生成AIが書くようになると、好まれるORMのアーキテクチャも変わるかもしれません。マッピングや振る舞いを抱え込む重いORMより、軽量なものが選ばれやすくなる可能性があります

どこかでまた機会があれば、「アプリケーションがデータを永続化すること」という領域にあるさまざまな問題について、整理したいと考えています。
