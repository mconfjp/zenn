## そもそもの手順
まずは生成AIなしでの書き方を整理します^[以前、[テックブログを書くときのやり方みたいなのを紹介したことがある](https://zenn.dev/levtech/articles/9c33c2f6aca805)んですが、まあ色々変わってるので改めて整理したいと思います]。自分がどのように記事を書いているのかをここで言語化し、生成AIで代替可能なところを切り出します。

### 手順の概要
手順はざっくり以下。細かく補足が必要な箇所はそれぞれ後に続けます。

- 企画：書きたいテーマをざっくり決める
- 調査：テーマについての下調べ。世の中でどんな議論がされているか調査
- 構成：ざっくりと構成を決めたのち、箇条書きレベルまで書く
- 執筆：箇条書きをもとに人が読める文章を作る
- 校正：間違った表現、事実誤認などの修正
- 編集：図を入れるなど、紙面にしたときに読みやすくする工夫をする
- 公開：公開

この７工程のうち、「企画・調査・構成」の前半３工程が作業の８割くらいを占めています。逆に後半４工程は箇条書きを読める日本語にしたりと機械的な作業です。
前半３工程については各工程のより詳しい内容を整理したいんですが、長々を書いてしまうと読んでいる皆さんが辛い思いをするので、以下にアコーディオンで隠しておきました。興味がある方は読んでもらって、さっさとAIの活用方法を教えろや、という方は次の章をお読みいただければと思います。

:::details 補足：前半３工程の詳しいところ
#### 補足：企画
- なにを書くか決めるところです。
- 「企画するぞ〜〜！！！」と思って企画するケースはあまりなくて、「XXのこと整理したいな...」というモヤモヤみたいなのが一定以上溜まった結果として企画として吐き出されることの方が圧倒的に多いです。気がついたら終わっている工程なんですが、ここがしっかりしてないと後の工程で苦しみます。
- なので言語化してみると、おそらく以下のようなことをやっている
	- 普段の生活の中で、自分の理解が及んでいない分野がいくつか出てくる
	- その中でもなんだか気になる箇所が出てくるので、気になる理由を整理する
	- その整理の中で、気になっている箇所が絞り込めたり、動機が明らかになる。それによって、以下がはっきりする
		- 記事を通して何が明らかになるか
		- 誰が気になってそうか
		- 調査する上でのワード、浅い仮説
#### 補足：調査
- なにについて書きたいか？　と言うのが整理できたら調査を入れます。すでに知っていることもあると思うけど、一旦調査を入れて、その分野における前提みたいなものを整理します。
	- マーケ的に言うと市場調査みたいなもん。ただマーケ観点というより、一旦みんながどこまで議論できててどこからは議論できてないかを把握しておくことで、話題についていけるようにしているというのが強い
- これをやっておくと、みんなが大体知ってるのはこのレベルで、自分が知りたいのはそこからどうはみ出していて、だからここを中心に置いてあげるとパンチの効いた記事になりそうだなとかがわかります
	- 例えばクエリチューニングの仕方をまとめたいな〜〜と思って調べてみると、インデックスの仕組みや実行計画の読み方は割と書かれていることが多いが、パフォーマンスを検証するための環境をどう用意するか？　みたいな観点が欠けていて実際にチューニングするときには困るよな...みたいなことがわかったりする。じゃあそこに注力するとパンチが効いてそうだし、というかシンプルに役立つから自分も嬉しいな、みたいな感じ
- 構成が見えそうだなってなってきたら構成に移る
#### 補足：構成
- 企画と市場調査が終わったらだいぶテーマとパンチラインがはっきりしているはず
	- それに沿って、どんなことを書くかをまとめる作業
- ここが一番好きで、構成作業の中で２つに分かれる
	- ざっくり構成
		- 大きな論の展開のさせ方を書いている
	- 細かい構成
		- 箇条書きまで書いてます
- その他
	- この構成作業はうまくいかなかったら調査をもうちょい挟むことが多いです。
	- というか、構成というか、調査を一旦やるとだいたいその分野のマインドマップと関係性みたいなものが整理できる
		- それを一旦ざっと書き出して、構造を把握する
		- ここは文章でやってもいいが、文章だとタイピングの速度が思考に追いつかないことが多いので、しゃべったものを文字起こししてもらうことが多い
	- で、そういうマインドマップを前提にしたときに、こういうテーマを書くと良さそうだよね、がわかる
		- かつ、そのオチってこうじゃない？　というのも、パッと仮定できる
		- その仮定が正しいことを明らかにするために追加調査が必要になって、改めて調べ直すことも多い
	- パフォーマンスチューニングの例でいうと
		- チューニングっていろんなものがあるが、特にDBのチューニングが俺は好き
		- DBのチューニングはインデックスかパラメータで大体分離できて、フルマネージドな環境が前提になった現代では特にインデックスがメインになる
		- インデックス設計は現代だと人間が見るよりはAIがほぼやってくれるのであまり人間が困ることはない
		- じゃあ課題になるのはどこか？
			- 問題を検知する箇所、実際にチューニングする箇所、デプロイ、統計のばらつきなど現実のデータが影響する箇所
			- 今回はチューニングの環境
		- チューニング環境はガチることもできるが、みんながそれやってたら大変すぎる
		- ガチらないチューニングを整理したい


- 調査した結果を図にしたり、喋ってまとめる
- ここでコンテキストマップを作っている
- もちろんテーマに沿っていない情報も入っているわけだが、ここでテーマに沿って取捨選択することで記事を尖らせている
- 次の箇条書きでも同じようにするとよさそう
- 同時に、熱意みたいなのも時間をかけて書く。これはAIを全く使わずに書くことが多い、雑念になっちゃうので使えない、身体を持ってない奴には書かれたくないなあ

### 連載ではどう変わったか？
- 連載での最も大きな変化はテーマに対して幾つかの論点に分けて論じる必要があるという点
- 連載の開始時に大きなテーマをぶち上げて、そこに合わせにいく感じで書いているので、若干無理をしている箇所もある
	- 具体的には、今回の連載はORMは単なるSQL発行器ではないだろう、という問題意識とともに書いていたが、全体を振り返るとSQL発行以外の責務はまばらであって、コアなものはないという結論に至った^[導入するシステムによっては他の責務は生まれるし、重要なものだけど、全てのケースでそうなるわけではないという話]
	- こういう当初の目論見が外れること自体も大きな成果ではあるが、シンプルにカッコ悪いのでちょっと誤魔化した面もある

## AI活用した手順
- ここからはAIをどう活用して書いたか？　という点
- それぞれ使えた度合いを星取表で表現する。星は置き換えの程度


| 作業  | 星     | 概要                    |
| --- | ----- | --------------------- |
| 企画  | ★☆☆☆☆ | あんま使ってない              |
| 調査  | ★★★☆☆ | かなり良かったが、人間の作業が多く残ってる |
| 構成  | ★★☆☆☆ | 壁打ちには使える              |
| 執筆  | ★★★★☆ | 使い方に工夫が必要だが、かなり便利     |
| 校正  | ★★★★★ | とても助かる                |
| 編集  | -     | 元々自分の担当ではない           |
| 公開  | -     | 元々自分の担当ではない           |


### 企画
#### 元々の進め方
- モヤモヤがあって勝手に企画になる
#### AIをどう使ったか？
- 連載タイトルとかには使った

### 調査
#### 元々の進め方
- ひたすらググって、資料を集めて、調査
#### AIをどう使ったか？
- 最も使う頻度が多かったが、人間の労力も多く残っていたため星は３つ。けど一番便利さを感じた部分ではある
- 具体の使い方は「調査資料の洗い出し」「資料読みのサポート」の２点
	- 前者はこういう資料を探してくれって頼んで資料をたくさん出してもらうやつ
	- 後者は資料を読みながら壁打ちしてもらう
		- https://zenn.dev/levtech/articles/claude-read-together
		- に書いた。今はこれをローカルのアプリにしてて、GUIで動かしている
### 構成
#### 元々の進め方
- 人力でざっくりとした構成、細かな構成を作っていく。上手くいかなかったら調査に戻る
#### AIをどう使ったか？
- ざっくり構成は基本的に自分で作る
	- 文字起こしのアプリを使ってて、それがおそらくAI文字起こし
	- あとその文字起こし原稿を構造化してもらうところに使ったりもしたが、イメージと違うので次第に使わなくなった
	- シンプルに文字起こしに使って、口頭で構成をまとめるときに聞いてもらう程度
- 箇条書きではパーツを探してもらうのに使った
	- 箇条書きをしながら、調査を進める必要がある
	- このときに、参考文献を改めて拾ってきてもらったり、自分が過去にメモしたノートを拾ってきてもらったりした
		- メモしたノートってのはこれのこと: https://zenn.dev/levtech/articles/mach-auch-zettelkasten
### 執筆
#### 元々の進め方
- 箇条書きの原稿を人力で読める文章に直していく
#### AIをどう使ったか？
- これはかなり使えたが、上手くいく使い方とうまくいかない使い方がかなりはっきり分かれた
- 上手くいく使い方
	- 箇条書きレベルですでに書いておいて、それを節（1,000文字程度）などの短い単位で渡し、綺麗な文章にしてもらうもの
		- これだとだいぶイメージに近い、上手な日本語を使ってくれる
		- 上手くいかないときは意図を伝え直し、生成し直してもらう
- 上手くいかないもの
	- 箇条書きのレベルが粗い
		- なんか違うなができる
		- これは結局、書きたい人が書きたいものをイメージしきれていないというだけ
	- 一度に全てを生成しようとする
		- 7000文字くらいを一気に生成すると、外れやすいのと、修正作業が並行してシンプルにやりにくい
		- これはもしかしたら、コードを生成してもらうときも、幾つかのコンポーネントに分けてコンポーネントごとに生成してもらったほうがやりやすいのかもしれない
### 校正
#### 元々の進め方
- 印刷した原稿を人力で読み、人力で修正
#### AIをどう使ったか？
シンプルに役立つ。俺はあんまり日本語のセンスがないので、大いに役立った。
使い方は以下
- 適切な語彙の選択
- 注釈に載せたい元ネタを探してきてもらう
- ファクトチェック
